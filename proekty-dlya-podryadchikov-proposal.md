## Что реально есть на портале прямо сейчас (проверено API)

- Механизм «Проекты» (в API — «рабочие группы», `sonet_group`, современная замена и Коллабам,
  и Экстранету) **уже активно используется** — 29 проектов с 2024 года.
- Часть из них — ровно то, что нужно: **проекты по отделам**, совпадающие со «Штатной
  структурой»: «Юридический отдел» (2 участника), «ДИСТРИБУЦИЯ» (3), «PR» (6), «Маркетинг» (8),
  «Работа с магазинами» (3). Плюс отдельные проекты по каждой разрабатываемой игре («Игра
  "О музыке"», «Игра "Гастрономия"» и т.д. — с 2024 года).
- Проверил состав участников каждого — **все участники всех проверенных проектов имеют тип
  «сотрудник»**, ни одного внешнего/гостевого человека пока никто не приглашал. То есть
  привычка пользоваться проектами внутри команды уже есть, а привычки звать туда подрядчиков
  — ещё нет. Это хорошая новость: людям не придётся осваивать новый инструмент, только новый
  сценарий использования знакомого.
- Отдельного проекта под «Отдел креатива» или «Отдел разработки» (в общем виде, не по
  конкретной игре) на портале не нашёл — если заводить проект для дизайнера/авторов текстов,
  его придётся создавать с нуля.

письма живому человеку — необратимое действие, я не стал делать это без вашего согласия.

## Два варианта организации — на решение владельца

**Вариант A — по отделам (соответствует уже начатой структуре).**
Завести «Отдел креатива» и «Отдел разработки» как отдельные проекты, по аналогии с уже
существующими «Юридический отдел»/«ДИСТРИБУЦИЯ»/«PR»/«Маркетинг». Плюс: единообразно с тем,
что уже прижилось. Минус: у всех подрядчиков отдела общий чат/задачи — Юля/Сергей/Александр/
Дмитрий увидят чужие задачи и переписку, если не разграничивать права внутри проекта.

**Вариант B — по конкретной игре/проекту** (как уже сделано для игр «О музыке», «Гастрономия»
и т.д. с 2024 года). Каждого подрядчика — в проект той игры, над которой он работает прямо
сейчас. Плюс: чище — никто не видит лишнего. Минус: если человек работает над несколькими
играми параллельно, придётся состоять в нескольких проектах; для Полины (дизайн, не привязана
к одной игре) этот вариант хуже подходит.

**Мой вариант по умолчанию:** гибрид — «Отдел разработки»/«Отдел креатива» как основной
проект-точка входа (общий чат, материалы), а под конкретную игру — задача внутри него со
ссылкой на нужный смарт-процесс/файлы, без создания отдельного проекта на каждую игру для
каждого подрядчика. Не настаиваю — это решение организационное, не техническое.

## Ограничение, которое нужно держать в голове

Внутри проекта **нет доступа к CRM** — ни к сделкам, ни к карточкам Выставок/Расходов/Договоров.
Если задача подрядчику завязана на конкретную CRM-запись (например, дизайн макета под
конкретную выставку) — ссылку/детали придётся указывать в тексте задачи вручную, подрядчик их
через портал сам не увидит.
