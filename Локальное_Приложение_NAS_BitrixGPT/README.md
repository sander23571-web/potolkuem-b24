# Б24 ⇄ Synology DSM — локальное приложение с совмещённой авторизацией

Обратный прокси, который показывает веб-интерфейс Synology NAS внутри Битрикс24.
Пользователь логинится один раз в Битрикс24, а прокси автоматически
авторизует его на NAS под своей учёткой.

## Как это работает

```
Пользователь → прокси (app.py) → OAuth Битрикс24 (проверка пользователя)
                                    ↓
                            учётка NAS (по e-mail или служебная)
                                    ↓
                            DSM веб-интерфейс (заголовки iframe убраны)
```

Прокси убирает из ответов NAS заголовки `X-Frame-Options` и
`Content-Security-Policy`, поэтому интерфейс можно встраивать в iframe.

---

## 1. Создание локального приложения в Битрикс24

1. Откройте **Маркетплейс → Для разработчиков → Разработчикам**.
2. **Готовые сценарии → Другое → Локальное приложение** → **Создать**.
3. Заполните **название** и **описание**.
4. В поле **Перенаправление (redirect URI)** укажите адрес прокси:
   `https://ваш-прокси.домен:8443/b24/callback`
5. Сохраните. Запишите два значения из приложения:
   - **Идентификатор приложения** (`client_id`, выглядит как `local.xxxx…`)
   - **Секретный ключ** (`client_secret`)

> Вкладка **Доступы/Разрешения** — добавьте право **user** (только чтение своего
> профиля), чтобы прокси мог определять пользователя через `user.current`.
> Права, необходимые для действий на портале, добавляйте по мере надобности.

Впишите эти значения в `config.json`:

| Поле | Что сюда |
|---|---|
| `APP_CLIENT_ID` | идентификатор приложения |
| `APP_CLIENT_SECRET` | секретный ключ |
| `APP_REDIRECT_URI` | адрес `/b24/callback` прокси |

## 2. Настройка прокси

Отредактируйте `config.json`:

- `PORTAL` — адрес вашего портала (по умолчанию стоит ваш).
- `SYNO_HOST` / `SYNO_PORT` — адрес NAS и порт (5001 = HTTPS, 5000 = HTTP).
- `SYNO_HTTPS` — `true`/`false`.
- `SYNO_DISABLE_VERIFY` — `true`, только если на NAS самоподписанный
  сертификат и вы осознаёте риск (в проде лучше исправить сертификат).
- `AUTH_MODE`:
  - `"service"` — все пользователи Б24 работают под одной служебной учёткой NAS
    (задаётся `SYNO_SERVICE_ACCOUNT` / `SYNO_SERVICE_PASSWORD`). Проще всего.
  - `"per-user"` — каждому пользователю Б24 своя учётка NAS. Тогда заполните
    файл `users.json`:
    ```json
    {
      "b24user@example.ru": { "account": "nas_user", "passwd": "пароль" }
    }
    ```
- `FLASK_SECRET` — замените на длинную случайную строку (для cookies сессии).

## 3. Установка и запуск

На сервере, где будет жить прокси (это не обязательно NAS — подойдёт любой
Linux-хост с доступом к NAS по сети):

```bash
pip install -r requirements.txt
python3 app.py
```

Прокси поднимется на `0.0.0.0:8443`. Проверьте:
- тест: `https://ваш-прокси:8443/` → должен увести на OAuth-страницу Битрикс24;
- после входа — открыть DSM.

### Обязательно для продакшена
- **HTTPS**. В примере dev-режим. Поставьте прокси за **nginx** (или gunicorn)
  и выпустите нормальный HTTPS-сертификат (Let's Encrypt). `redirect_uri`
  должен совпадать с фактическим адресом.
- **Отключите самоподписанный SSL прокси** (`ssl_context="adhoc"` — только
  для локального теста).
- Запускайте как сервис: systemd/nginx.

## 4. Как показать внутри Битрикс24

Локальное приложение в Битрикс24 умеет регистрировать свои **страницы
приложения** (тип `PAGE`). В интерфейсе разработчика у приложения настройте
встраиваемую страницу и укажите в качестве содержимого адрес прокси
(`https://ваш-прокси:8443/`) — Битрикс24 откроет её iframe'ом. Так интерфейс
NAS появится прямо на внутренней странице портала.

Альтернатива на старте: просто добавьте ссылку на прокси в меню портала
(например, в «Задачи и проекты» или на главной).

> Примечание: прямая авторизация пользователя делается через страницу
> приложения. Если используете обычную ссылку — сработает тот же OAuth-поток,
> просто в отдельной вкладке.

## Ограничения и что доработать

- DSM активно использует WebSocket (File Station, Terminal). В примере
  проксируется только HTTP. Для полноценной работы WebSocket в nginx нужно
  пробросить `upgrade` заголовки, а в прокси — поддержку WebSocket (например,
  через расширение Flask).
- В примере **одна общая сессия** на всех пользователей (простота). Для
  одновременной работы нескольких людей лучше держать сессию Synology
  в Flask-сессии каждого пользователя отдельно.
- Некоторые подсистемы DSM зашиты на абсолютные пути/поддомены, в редких
  случаях могут потребоваться точечные правки переписывания пути.
- Синхронизация учёток (создание пользователя в Б24 → автосоздание на NAS)
  в этот пример не включена — можете попросить, добавлю отдельным скриптом.
