## 1. Снято: «второй портал» — скорее всего один и тот же портал под двумя именами

`b24-0l7a4f.bitrix24.ru` (упоминается в `b24-api-patterns.md` и в `.claude/settings.local.json`) и `potolkuem.bitrix24.ru` (используется в gigaclaude/Sklad/bikonstruct) — с высокой вероятностью **один и тот же облачный портал Б24** под двумя валидными именами: `b24-xxxxx.bitrix24.ru` — технический авто-домен, который Битрикс24 выдаёт при создании портала, `potolkuem.bitrix24.ru` — читаемый алиас поверх него (штатная функция Б24, оба имени резолвятся в один и тот же портал).

Подтверждение косвенное, но конкретное: сущность «Выставки» в `talk/b24-api-patterns.md` (через `b24-0l7a4f`) имеет `entityTypeId=1048` — и ровно тот же `entityTypeId=1048` используется в `Bitrix24/bikonstruct/scripts/backfill.js` (через `potolkuem.bitrix24.ru`) для `EXHIBITION_ID`. Один и тот же числовой ID сущности с двух разных «порталов» на практике означает один портал.

**Что сделать:** один API-вызов (`app.info` или `crm.type.list` на оба домена, сравнить `portal_id`/`member_id` в ответе) закроет вопрос окончательно. После подтверждения — в `b24-api-patterns.md` дописать явно: «`b24-0l7a4f.bitrix24.ru` = технический домен для `potolkuem.bitrix24.ru`, тот же портал», чтобы это не переоткрывалось как загадка при следующем аудите.

## 2. Реальная находка: `consent-service/` — целый непрописанный сервис

`talk/consent-service/` — отдельный Node.js-сервис (деплоится как Yandex Cloud Function, судя по `consent-yandex.zip`) для согласий 152-ФЗ. Не упомянут **нигде** в `CLAUDE.md`/`DASHBOARDS.md`/`STATUS.md` talk — то есть это ровно тот случай, который мы ищем: сущность, существующая в коде, но отсутствующая в описании проекта.

По гигиене секретов сам сервис в порядке: `B24_WEBHOOK` читается из `process.env`, реальный `.env` не в git (только `.env.example`), zip-бандл для деплоя не содержит захардкоженных секретов (проверено — только код/`node_modules`).

**Что сделать:** дописать `consent-service` в `CLAUDE.md`/`STATUS.md` — назначение, куда задеплоен, кто им пользуется. Действия менять не требует, только документацию.

## 3. Файлы, попавшие в git до появления правила `.gitignore`

У talk `.gitignore` неожиданно лучше, чем у корневого `Bitrix24` (там нет `*.xlsx`, здесь — есть, `*.xlsx`/`*.docx`/`*.png`/`Снимок*` все перечислены). Но правило не ретроактивно: часть файлов была закоммичена раньше и осталась в индексе, несмотря на игнор:

- `GOTOVO/KPI (1) (3).xlsx`, `NONFICTION/KPI nonfiction.xlsx` — открыл, shared-strings пустые (мало текстового содержимого, похоже на в основном числовые данные) — не выглядит как утечка персональных данных, но по смыслу («KPI» = показатели эффективности, потенциально сотрудников) не должно быть в git по той же логике, что и остальной `.gitignore`.
- `Sklad/Razmery.xlsx`, 17× `Sklad/image*.png` — судя по имени, размеры товаров и фото склада, не персональные данные.

**Что сделать:** `git rm --cached` для этих файлов (оставить на диске, убрать из индекса) — раз правило `.gitignore` уже есть и отражает намерение, файлы, добавленные до правила, стоит привести в соответствие с ним же. Не критично, гигиена.

## 4. `EMAILINGS.txt` — переписка в git, умеренная чувствительность

Закоммичен, содержит заголовки/тело одного пересланного письма — реальные ФИО и email двух сторон переписки (один из которых, Репников Антон, — внутренний сотрудник, уже фигурирует в списке менеджеров `potolkuem` в `CardScanner/ПЛАН_ПРОЕКТА.md`, то есть не внешний клиент). Похоже на материал для разбора проблемы с доставкой писем, не утечка клиентской базы. Ниже приоритетом, чем находки в gigaclaude/BPTP, но по той же логике — переписка конкретных людей не обязана лежать в git.

**Что сделать:** по желанию — `git rm --cached`, если файл больше не нужен как рабочий материал.
