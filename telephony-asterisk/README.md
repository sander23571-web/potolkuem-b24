## 0. Аналитика: зачем вообще Asterisk (а не облачная АТС провайдера)

Ниже — трезвый взгляд, стоит ли вообще инвестировать в интеграцию Asterisk, или предложить
АДАТ переезд на готовую «виртуальную АТС» провайдера с нативной поддержкой Б24. Не влияет на
решение «Итгрикс vs AsterX» — но должно быть озвучено владельцу/АДАТ до начала работ, т.к.
может изменить всю задачу.

**Тезис (гипотеза владельца):** Asterisk — способ сэкономить на ПО провайдера телефонии;
у большинства провайдеров есть свои продукты, полностью заменяющие Asterisk; возможности
Asterisk велики, ПО провайдера редко дотягивает до такого уровня управления, но в большинстве
случаев этот функционал избыточен и содержание не оправдано.

**Разбор — верно частично, две разные оси смешаны:**

**Ось 1 — деньги.** Экономия часто мнимая. Asterisk бесплатен как ПО, но не бесплатна
эксплуатация:
- содержание сервера/VM (электричество, бэкапы, сам хост — в случае АДАТ это ESXi);
- труд администратора, который понимает SIP/NAT/dialplan/безопасность;
- риск **toll fraud** — незапатченный или плохо настроенный Asterisk, доступный из интернета,
  классическая цель взлома с накруткой платных международных звонков (суммы ущерба — до
  сотен тысяч рублей за одну ночь). Реальная, а не гипотетическая статья расходов, если
  администрировать AMI/SIP-доступ будет некому.

Расход просто переезжает из статьи «подписка провайдеру» в статьи «труд» + «риск», причём
вторая обычно куда менее заметна руководству до первого инцидента.

**Ось 2 — контроль/кастомизация.** Здесь возможности Asterisk объективно на порядок шире
любого коробочного продукта: гибкий dialplan, AMI/AGI/ARI, объединение нескольких SIP-транков
и провайдеров одновременно (резервирование), сложная маршрутизация/скилл-роутинг, интеграция
с чем угодно, полный контроль над хранением записей разговоров (комплаенс/безопасность).
Эта мощь оправдана, когда есть реальная потребность хотя бы в одном из пунктов; для типового
сценария малого бизнеса «звонок → карточка CRM» — чаще всего оверинжиниринг.

**Практический вывод:** раз Asterisk у АДАТ уже стоит и работает — это sunk cost, переезд ради
одной только интеграции с CRM может быть не оправдан. Но стоит явно спросить владельца/АДАТ,
**почему у них Asterisk, а не облачная АТС провайдера** (Манго Офис, ЮИС, Novofon, MTS Exolve,
Билайн, Zadarma и др. — у большинства есть готовая нативная интеграция с Б24 в 2-3 клика, без
всякого моста AMI→REST). Если причина не входит в список выше (масштаб/кастомная логика/
комплаенс/резерв провайдеров), а «так исторически сложилось» — честно посчитать и сравнить:
стоимость нашей интеграции + риски содержания Asterisk против переезда на готовую АТС
с уже встроенной поддержкой Б24. Это может оказаться дешевле и надёжнее того, что мы
собираемся строить ниже.

## 0.1. Развилка: интеграция через Asterisk vs напрямую с провайдером связи

Отдельный вопрос от раздела 0 (тот — «нужен ли вообще Asterisk», этот — «даже если Asterisk
остаётся, обязательно ли интегрироваться именно с ним, а не с оператором связи, чей номер
АДАТ и так использует»).

**Технически возможно интегрироваться напрямую с провайдером**, минуя мост к Asterisk —
но только если сам провайдер (тот, кто выдал SIP-транк/номер) предоставляет API или готовую
нативную интеграцию с Б24 (как у Манго Офис, ЮИС, Novofon, MTS Exolve, Билайн Бизнес,
Zadarma и т.п.). **Открытый вопрос — кто именно провайдер у АДАТ и есть ли у него такой API**
— без этого ответа пункт неприменим, нужно уточнить у АДАТ при следующем контакте.

**Ключевое ограничение прямой интеграции с провайдером — видимость только на уровне транка.**
Провайдер видит: звонок пришёл/ушёл с номера, длительность, время. Всё, что происходит
**после** того, как звонок попал в Asterisk — какой внутренний номер (extension) ответил,
переводы между сотрудниками, время на удержании, выбор в IVR-меню — провайдеру не видно:
это состояние живёт только внутри Asterisk.

| Критерий | Через Asterisk (мост AMI→REST) | Напрямую с провайдером |
|---|---|---|
| Факт звонка в карточке CRM | ✅ | ✅ (если у провайдера есть API) |
| Кто из сотрудников ответил | ✅ | ❌ — провайдер не знает про internal extensions |
| Запись разговора | ✅ (Asterisk пишет локально) | ⚠️ обычно нет — провайдер редко пишет на своей стороне; если и пишет — то без привязки к сотруднику |
| Click-to-call из Б24 на сотрудника | ✅ (через мост + AMI Originate) | ❌ — провайдер не может дозвониться до внутреннего IP-телефона, тот адресуем только внутри Asterisk |
| Сложность внедрения | Выше (мост, VM, AMI-доступ — см. План) | Ниже, если у провайдера уже есть готовая интеграция с Б24 |

**Вывод:** прямая интеграция с провайдером оправдана, только если АДАТ реально не нужна
пооператорская детализация (просто факт звонка с клиентом, без записи и без атрибуции
сотруднику). Если важны запись разговоров и понимание, кто из менеджеров обработал звонок
(для CRM-аналитики продаж это обычно и есть основная ценность интеграции телефонии) —
без моста к Asterisk не обойтись, провайдер этого не знает в принципе.

## 1. Официальный механизм Битрикс24

**Встроенный UI** (Телефония → Подключение → «SIP АТС» / «Офисная SIP АТС»): можно
подключить произвольный SIP-транк логином/паролем/адресом сервера — в том числе от
своего Asterisk. Входящие звонки — бесплатно; для исходящих/переадресации после
пробного периода нужна платная лицензия «SIP-коннектор».

Это даёт только базовую SIP-регистрацию (звонок идёт, номер определяется), **но не даёт**
привязки к карточкам CRM, записи разговора, кастомной маршрутизации — для этого нужен
REST API.

**REST API «Телефония» (`telephony.*`)** — официальный способ для внешней АТС:

| Метод | Назначение |
|---|---|
| `telephony.externalLine.add/update/get/delete` | Регистрация внешней линии |
| `telephony.externalCall.register` | Регистрация начала звонка (обязателен для CRM-активности) |
| `telephony.externalCall.finish` | Завершение звонка |
| `telephony.externalCall.attachRecord` | Прикрепление записи разговора |
| `telephony.externalCall.show/hide` | Показ/скрытие карточки звонка |
| `telephony.externalCall.searchCrmEntities` | Поиск клиента/ответственного по номеру |
| `telephony.call.attachTranscription` | Транскрипция |
| События `OnExternalCallStart` / `OnExternalCallBackStart` | Click-to-call / callback-формы |

Группа `voximplant.*` относится к встроенной облачной АТС Б24, для внешнего Asterisk не нужна.

Документация: [Telephony: Overview of Methods](https://apidocs.bitrix24.com/api-reference/telephony/index.html),
[telephony.externalCall.register](https://apidocs.bitrix24.com/api-reference/telephony/telephony-external-call-register.html),
[требования к телефонным интеграциям](https://apidocs.bitrix24.com/market/preparing-to-publish/requirements-telephony.html)
(по сути эталонная схема архитектуры моста).

## 3. Самописный мост (если готовые варианты не подойдут)

Стандартный паттерн (его же используют AsterX и asterlink):

1. Слушать события Asterisk через **AMI** (`Newchannel`, `Dial`, `Bridge`, `Hangup`).
   ARI (более новый REST/WebSocket интерфейс Asterisk) в найденных решениях не встречен —
   везде используется AMI.
2. Старт звонка → `telephony.externalCall.register` (уникальный `EXTERNAL_CALL_ID`, номер линии).
3. Завершение → `telephony.externalCall.finish`.
4. Если есть запись — конвертировать (обычно MP3) → `telephony.externalCall.attachRecord`.
5. Роутинг по звонящему — `telephony.externalCall.searchCrmEntities`.
6. Click-to-call из Б24 — подписка на `OnExternalCallStart`; callback-формы — `OnExternalCallBackStart`.

## 4. Вывод и рекомендация

Доступы к АТС АДАТ уже есть (23.09.2026):
- Веб-интерфейс Asterisk: `http://192.168.1.69/admin/` — путь `/admin/` указывает на **FreePBX**
  поверх Asterisk (у голого Asterisk такого GUI из коробки нет). Требует подтверждения на месте,
  но если так — это упрощает выбор: и Itgrix, и informUnity, и AsterX ориентированы в первую
  очередь именно на FreePBX.
- ESXi (VMware), где живёт виртуалка АТС: `https://192.168.1.47/ui`
- Веб-интерфейс IP-телефонов — адрес не зафиксирован, уточнить.

⚠️ Все адреса — внутренняя локальная сеть АДАТ (192.168.1.x), из облачной рабочей сессии
недоступна напрямую. Нужен VPN/проброс в эту сеть или доступ через кого-то, кто физически
в ней (или через RDP/TeamViewer на машину в этой сети).

**Ещё не выяснено:** точная версия FreePBX/Asterisk, число операторов/линий, доступность
AMI-порта (обычно 5038) для внешнего подключения — без него ни один из вариантов (Itgrix,
informUnity, AsterX, самописный мост) не заработает, т.к. все они читают события звонков
именно через AMI.

Своя разработка с нуля через AMI+REST **не оправдана** — паттерн полностью стандартный и уже
реализован в открытом коде и в коммерческих приложениях. Строить велосипед имеет смысл только
если понадобится нестандартная логика маршрутизации, которую не покрывают готовые варианты.

**Рекомендуемый порядок пилота:**
1. Уточнить у АДАТ дистрибутив Asterisk и доступность AMI-порта с сервера, откуда будем стучаться в Б24.
2. Попробовать **estvita/AsterX** (бесплатно, open-source, активно поддерживается) — минимальный риск, можно быстро откатить.
3. Если нужна коммерческая техподдержка / меньше рисков внедрения своими силами — сравнить триалы **Itgrix** и **informUnity** на реальном Asterisk клиента.

## 5. План внедрения (пошагово, с пояснениями)

Написан с расчётом на то, что процесс Asterisk/FreePBX подзабылся — каждый шаг с «зачем».

### Фаза 0 — Аудит и решение «строить или мигрировать»

1. **Обсудить с владельцем/АДАТ раздел 0 (аналитика)** — прежде чем тратить часы на мост,
   решить: остаёмся на Asterisk или пересаживаемся на облачную АТС провайдера. Если остаёмся —
   переходим к следующим шагам.
2. **Снять аудит текущей АТС** (в FreePBX GUI, `http://192.168.1.69/admin/`):
   - Точная версия FreePBX и Asterisk (Admin → System Admin → Info, или в консоли
     `fwconsole --version` / `asterisk -rx "core show version"`).
   - Список транков (внешние SIP-линии к оператору связи) — Connectivity → Trunks.
   - Список внутренних номеров (Applications → Extensions) — сколько операторов, кто есть кто.
   - Включена ли запись разговоров и в каком формате (обычно WAV, коннекторы обычно сами
     конвертируют в MP3 перед отправкой в Б24).
   - Есть ли уже открытый наружу порт AMI (5038) или он торчит только на `127.0.0.1`
     (дефолт FreePBX/Asterisk из соображений безопасности — почти наверняка так и есть,
     это нормально и ожидаемо, а не проблема).
3. **Зафиксировать список ответственных менеджеров** — сопоставление «внутренний номер
   Asterisk (extension) ↔ пользователь Б24» понадобится для маршрутизации звонков и показа
   карточки нужному сотруднику.

*Зачем:* без этого аудита нельзя обоснованно выбрать между AsterX/Itgrix/informUnity — они
по-разному ведут себя в зависимости от версии FreePBX и списка транков.

### Фаза 1 — Выбор решения

Решить по итогам Фазы 0 и раздела 4: пилот на **AsterX** (по умолчанию, бесплатно) или
триал **Itgrix/informUnity** (если хочется готовой поддержки и меньше возни своими руками).
Ниже план для AsterX — для коробочных решений шаги 2-4 заменяются установкой приложения
через Маркетплейс Б24 по инструкции разработчика, дальше (Фаза 5 и далее) — общие.

### Фаза 2 — Подготовка окружения (сеть и хостинг моста)

1. **Где разместить мост:** отдельная лёгкая VM на том же ESXi (`https://192.168.1.47/ui`),
   не сама FreePBX-машина — так апдейт/сбой моста не трогает продакшн-АТС, и наоборот.
2. **Сетевые требования моста:** одновременный доступ (а) в локальную сеть АДАТ до Asterisk
   по AMI-порту (TCP 5038) и (b) наружу в интернет до `potolkuem.bitrix24.ru` (REST API).
   Если у VM моста нет прямого выхода в интернет — потребуется NAT/проброс на роутере офиса.
3. **Открыть AMI для моста** (в `manager.conf` FreePBX/Asterisk):
   - Создать **отдельного** manager-пользователя для моста (не переиспользовать admin) —
     минимально нужные права: чтение событий звонков (`read = call,agent`), при необходимости
     `originate` для click-to-call.
   - Ограничить доступ по IP только адресом VM-моста (`permit=<IP моста>/255.255.255.255`).
     AMI **никогда** не выставлять в интернет напрямую — это прямой путь к toll fraud.
   - Перечитать конфиг (`fwconsole reload` или `asterisk -rx "manager reload"`).

*Зачем именно так:* AMI-протокол не шифрован и даёт доступ к управлению звонками — при
компрометации это открытая дверь на АТС. Отдельный пользователь с урезанными правами и
IP-whitelist — стандартная защита при таком мосте.

### Фаза 3 — Подготовка стороны Битрикс24

1. Проверить права текущего вебхука (`B24_WEBHOOK` в `.env` talk-проекта) — есть ли доступ
   к методам `telephony.*`; если нет — завести отдельный входящий вебхук/локальное приложение
   с нужным scope (`telephony`), не расширять права основного вебхука без необходимости.
2. Зарегистрировать внешнюю линию: `telephony.externalLine.add` → получить `LINE_NUMBER`,
   привязать к ней логичное имя (например, «АДАТ — основная линия»).
3. Сверить список пользователей Б24, которые должны видеть звонки/делать click-to-call
   (сопоставление с extensions из Фазы 0, шаг 3).

### Фаза 4 — Установка и настройка моста (AsterX)

1. Развернуть AsterX на VM-мосту (по инструкции репозитория — Docker или venv, уточнить
   по актуальному README проекта на момент установки, т.к. в этой сессии код AsterX не
   изучался построчно, только описание проекта).
2. Прописать в конфиге AsterX: адрес/креды AMI (Фаза 2), адрес портала + вебхук/OAuth-креды
   Б24 (Фаза 3), маппинг extension → пользователь Б24 (Фаза 0).
3. Запустить как сервис (systemd) — чтобы мост поднимался сам после перезагрузки VM.

### Фаза 5 — Пилотное тестирование

Тестировать сначала на 1-2 внутренних номерах, не на всех сразу:

1. **Входящий звонок** на тестовый номер → проверить, что в Б24 появилась активность/звонок
   в карточке нужного лида/сделки/контакта (поиск по номеру через
   `telephony.externalCall.searchCrmEntities`).
2. **Исходящий звонок** — обычный (менеджер набрал руками) и **click-to-call** из карточки Б24.
3. **Запись разговора** — появляется ли файл, прикреплённый к активности звонка в Б24.
4. **Одновременные звонки** — проверить, что мост не теряет события при 2+ параллельных
   разговорах (частая проблема самописных/сырых мостов).
5. **Пропущенный звонок** — корректно ли отражается в Б24 (не как отвеченный).

### Фаза 6 — Раскатка на всех и обучение

1. Добавить остальные внутренние номера/транки в конфиг моста.
2. Короткая инструкция сотрудникам: как теперь выглядит звонок в карточке CRM, как звонить
   по кнопке из Б24, где искать запись разговора.
3. Базовый мониторинг: жив ли сервис моста (например, простой systemd + алерт при падении,
   или ручная периодическая проверка первое время).

### Фаза 7 — План отката

Если мост ведёт себя нестабильно — остановить сервис моста на VM, при необходимости отключить
manager-пользователя моста в `manager.conf` АТС. Продакшн-FreePBX это не затрагивает —
именно поэтому мост размещается на отдельной VM, а не на самой АТС (см. Фазу 2).
