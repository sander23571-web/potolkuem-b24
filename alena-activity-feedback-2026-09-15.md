## 2. Одна публикация = одна карточка (мультиплатформенность)

Сейчас поле `ufCrm42SmPlatform` — **одиночный** enum (`isMultiple: False`, подтверждено живым
`crm.item.fields`). Значит нельзя просто отметить несколько площадок в одном поле без изменения
структуры — нужна доработка.

**(а) Осуществимость:** да, стандартный паттерн Б24 (СП «Съёмки» в этом же типе уже использует
множественный enum `ufCrm42SUsage` для похожей задачи «где использовано» — прямой прецедент
внутри того же СП).

**(б) Конкретно:**
- Поле `UF_CRM_42_SM_PLATFORM` (id поля 174 надо будет уточнить при исполнении через
  `userfieldconfig.get`) сделать **множественным**. **Грабля проекта (`talk/CLAUDE.md`, п.15):**
  флаг `multiple` нельзя поменять через `userfieldconfig.update` — API отвечает успехом, но
  значение не меняется. Единственный рабочий путь — **удалить поле и создать заново** с тем же
  кодом `UF_CRM_42_SM_PLATFORM`, `multiple: "Y"`, тем же enum-списком (+YouTube/RUTUBE из п.1).
  Существующие значения в уже заведённых карточках при удалении поля **будут потеряны** — нужно
  заранее выгрузить текущие значения (`crm.item.list` по категории 60, поле
  `ufCrm42SmPlatform`), чтобы после пересоздания поля восстановить их вручную/скриптом как
  массив из одного элемента.
- Ссылка на публикацию (`ufCrm42SmLink`, сейчас одиночный `url`) — нужно продублировать по
  каждой площадке. Два варианта:
  - **Проще:** сделать это же поле `multiple: "Y"` (та же операция удаления/пересоздания, можно
    одним заходом с полем платформы) — но тогда теряется соответствие «эта ссылка — для этой
    площадки» (просто список ссылок без привязки к конкретной платформе).
  - **Точнее (рекомендую):** завести **отдельные url-поля по площадкам** —
    `UF_CRM_42_SM_LINK_VK`, `..._TG`, `..._ZEN`, `..._MAX`, `..._TIKTOK`, `..._YT`,
    `..._RUTUBE`, `..._INSTAGRAM`, `..._OTHER` (9 полей типа `url`, показывать в UI только те,
    что нужны). Немного громоздко в конструкторе карточки, но однозначно и не требует удаления
    существующего поля `ufCrm42SmLink` (можно оставить как «основную» ссылку для обратной
    совместимости со старыми записями, потом решить, выводить её на дашборде или нет).
- Поля статистики (`Просмотры`/`Охват`/`Лайки`/`Комментарии`/`Репосты`) — вопрос открыт (см. п.3):
  если статистика по-прежнему нужна **по каждой площадке отдельно** (что логично для сверки с
  LiveDune, который считает per-account, не per-post-across-platforms), эти 5 double-полей тоже
  придётся продублировать ×9 площадок (или оставить одно поле «сводные просмотры» = сумма).
  Это прямо влияет на объём доработки — решить вместе с Алёной, нужна ли ей разбивка по
  площадкам в самой карточке, или сводная цифра устраивает.

**(в) Доп. разработка:** обязательно — правка `report-app/activity-data.js` (SELECT новых
полей, суммирование статистики по площадкам) и `render-activity.js` (таблица публикаций,
`socialTable()`) — умеренный объём, т.к. структура таблицы построена на одной платформе на
строку, придётся переделать на список площадок в одной строке (бейджи вместо одного бейджа).

**(г) Открытые вопросы:**
1. Нужна ли статистика **по каждой площадке отдельно внутри одной карточки**, или достаточно
   одной сводной цифры на публикацию? Определяет, дублировать ли 5 полей статистики ×9 или нет.
2. Подтвердить у Алёны схему потери данных при пересоздании поля платформы — **нужен экспорт
   текущих значений до операции** (сколько записей уже занесено на 15.09 — уточнить перед
   исполнением, `crm.item.list` filter categoryId=60 count).
3. Отдельные url-поля по площадкам (9 штук) vs один множественный url без привязки к площадке —
   решить с Алёной, что удобнее вносить руками.

## 7. Задачи Б24 → автоматически в её CRM-процесс

**(а) Осуществимость:** да, но **не через `event.bind`** — этот метод **не работает с вебхуком**
на этом портале (протестировано и задокументировано 21.06.2026 именно на потолкуемовском
портале — `Bitrix24/knowledge-base/05_решения/PROJECTS_TECH_FINDINGS.md`, раздел 12: `error:
WRONG_AUTH_TYPE`, «текущий тип авторизации запрещён для этого метода»). Но есть **рабочий
прецедент на этом же портале** — отдельный от `event.bind` механизм: **исходящий вебхук**,
настроенный вручную в UI портала (Профиль → Разработчикам → Другое → Исходящий вебхук,
событие `ONTASKADD`), который шлёт `POST` с form-encoded данными задачи на публичный endpoint
без API-ключа. Это уже используется на потолкуемовском портале для другой задачи: `/hooks/
potolkuem/task-auditor` (файл `Bitrix24/ENVPro/proxy/main.py:314`) — при создании любой задачи
добавляет руководителя в наблюдатели. Значит инфраструктура для «событие создания задачи →
что-то сделать в Б24» уже развёрнута и проверена вживую на этом портале, задачу 7 можно решить
тем же паттерном.

**(б) Конкретно:**
1. Новый endpoint в `ENVPro/proxy/main.py` (или расширение существующего `task-auditor`, но
   отдельный чище): `POST /hooks/{portal}/task-to-activity`.
2. В UI портала `potolkuem.bitrix24.ru` зарегистрировать **второй исходящий вебхук** на
   `ONTASKADD` → URL `https://b24proxy.bobp.ru/hooks/potolkuem/task-to-activity` (или использовать
   тот же вебхук, если Б24 позволяет несколько обработчиков на одно событие — не проверял,
   проще завести второй явно).
3. Логика: если `data[FIELDS_AFTER][RESPONSIBLE_ID]` == 104 (Алёна) — создать элемент в СП 1100:
   - `entityTypeId: 1100`, **новая 5-я (или 6-я, если сделали и п.5) категория «Входящие /

Docker-пересборка `docker compose up -d --build`), регистрация исходящего вебхука в UI портала

дашборда (учитывать новую категорию в `activity-data.js`/`render-activity.js`, иначе такие
задачи будут «невидимы» на `/report/creative`, пока Алёна их не разберёт).

**(г) Открытые вопросы:**
1. **Перенос элемента между категориями внутри одного СП** — стандартно предполагается, что
   для динамических СП (в отличие от классических сделок, где `CATEGORY_ID` через API молча не
   меняет воронку — грабля проекта №5) `categoryId` **можно** менять через `crm.item.update`, но
   **это не проверено вживую на этом портале** ни в одной из прошлых сессий — до реализации
   нужен короткий пилот на тестовом элементе (без переноса реальных задач), чтобы не повторить
   ту же грабл, что уже была с классическими сделками.
2. Что происходит с исходной задачей Б24 после того, как Алёна перенесла информацию в СП —
   закрывать её автоматически (риск: задача может быть общей/групповой не только для неё) или
   оставить закрытие на ней вручную? Предлагаю **не автоматизировать закрытие** на первом шаге —
   меньше риска потерять что-то, ответственность за корректность остаётся у человека.
3. Нужно ли фильтровать по типам задач (например, не заводить в СП технические регламентные
   задачи вроде авто-задач из cron, если Алёне ставят и такие) — уточнить у неё, какие именно
   задачи сейчас дублируются вручную, чтобы не заводить лишний шум в СП.
4. `UF_CRM_TASK` (штатная привязка задачи к CRM, см. `CARDSCAN_PATTERNS.md` п.6) документирован
   только для классических сущностей (`CO_`/`C_`/`D_`/`L_`) — не подтверждено, поддерживает ли
   он привязку к элементам динамических СП (`entityTypeId >= 1000`). Если да — можно было бы
   привязать задачу к элементу СП 1100 напрямую («видно из задачи» в обе стороны), но это
   опциональное усиление, не блокер для базового варианта (ссылка текстом в `ufCrm42Comment`
