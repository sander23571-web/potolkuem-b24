# Получение согласия на рассылку («Тук-Тук») — найденный нативный механизм Б24

> Создано: 24.09.2026. Статус: механизм найден и подтверждён живым тестом, требует финальной
> доводки текста согласия перед реальным запуском. Продолжение — 25.09.2026 очно в офисе АДАТ.
> Задача: у части контактов (собраны на выставках и др. способами) нет формального согласия
> на рекламные рассылки — нужно собрать согласие рассылкой без нарушения ст.18 №38-ФЗ «О рекламе».

---

## Главный вывод: у Б24 уже есть встроенный double opt-in — все самописные варианты отклонены

По ходу дня рассматривались и отклонены: самописный `consent-service` (Node + Yandex Cloud
Functions), кастомная CRM-форма с ручным зеркалированием согласия на поле Контакта. Все они
избыточны — у штатного инструмента **CRM → Маркетинг → Email-рассылки** есть встроенный
механизм ровно под эту задачу.

### Как это работает (подтверждено официальной справкой Б24 + живым тестом)

В редакторе кампании, раздел «Дополнительно» → чекбокс **«Подтверждение согласия на
рассылку»** + выпадающий список «Выберите соглашение»:

1. При отправке кампании контактам **без подтверждённого согласия** уходит не сама кампания,
   а отдельное письмо-запрос (генерируется самим Б24, свой нейтральный шаблон — картинка +
   текст согласия + две кнопки «Получать»/«Нет, не присылайте мне ничего»), **один раз**.
2. Как только контакт нажимает «Получать» — **автоматически, без повторной ручной отправки**,
   ему уходит содержимое самой кампании.
3. Лимит: **500 запросов согласия за раз**; если аудитория больше — остаток уходит автоматически
   порциями, следующая партия — через 7 дней (или раньше, когда освобождается место по ответам).
   Дробить вручную не нужно, всё через одну кнопку «Отправить».
4. Если галочка включена, а шаблон согласия не выбран — **рассылка не отправится вообще**
   (встроенная защита от отправки рекламы без основания).
5. Источники: `helpdesk.bitrix24.ru/open/22952868`, `/open/23019390`,
   `helpdesk.bitrix24.com/open/23269576`, `/open/25753267` — цитаты идентичны в ru/en версиях.

**Не подтверждено официально:** отдельная кнопка **«Отправить согласие на рассылку»**
(соседняя с обычной «Отправить») нигде не описана в документации — но она реально существует
в интерфейсе и была использована для теста (см. ниже), судя по всему это более новая функция.
Предположительно — ручной способ разово разослать только запросы согласия, не трогая
отправку самой кампании, но это не подтверждённый факт, а вывод по наблюдению.

## Живой тест (24.09.2026) — механизм подтверждён end-to-end

Отправили тестовое письмо-запрос через кнопку «Отправить согласие на рассылку» на
`sander23571@gmail.com`. Разобрали реальный HTML-исходник письма:

- Тема: «Вы согласны получать наши рассылки?» — фиксированная, генерируется Б24, не наш текст.
- Две настоящие рабочие кнопки (не декоративные) — `<a href>` на
  `https://ru-potolkuem.mailinetservice.com/ru.potolkuem/pub/mail/consent.php` с параметрами
  `consent=apply` / `consent=reject`, подписанными криптографическим хэшем (подделать нельзя).
- В `tag` — `{"CODE":"email","POSTING":"18","CONSENT":12}`: привязка к конкретному
  контакту, конкретной кампании (`POSTING`) и конкретному шаблону согласия (`CONSENT`).
- **Важно:** тест ушёл с шаблоном **id=12**, не id=14 (см. ниже, какой шаблон реально лучше) —
  при настройке реальной отправки нужно явно выбрать нужный шаблон, дефолт может быть не тот.
- Клик по «Получать» **реально дошёл до Б24** — создал запись в реестре «Согласия
  пользователей» (Центр продаж → Соглашения → Список полученных согласий), привязанную к
  `POSTING=18`. Три клика подряд = три отдельные записи (реестр append-only, дублей не
  схлопывает — это ожидаемо, не баг: подтверждённое ранее официальным источником юридическое
  требование неизменяемости журнала согласий).
- Подписи у кнопок («Получать» / «Нет, не присылайте мне ничего») **зашиты самим Б24**, не
  берутся из текста шаблона согласия — путаница с «в письме нет кнопки» была чисто визуальной
  (кнопки есть и в коде, и на скриншоте письма).

**Стратегически важный вывод:** письмо-запрос согласия — это отдельный, нейтральный, системный
шаблон Б24, а не наш кастомный текст «Тук-Тук» с брендированным лого/слоганом. Наш текст
«Тук-Тук» уходит только **после** подтверждения — то есть уже согласившемуся человеку, где
юридический риск по ст.18 №38-ФЗ существенно ниже. Раньше опасались, что бренд/слоган в
«Тук-Тук» может быть расценен как реклама без согласия — при использовании штатного чекбокса
этот риск снимается: сам «запрос» нейтрален, брендированный контент идёт только тем, кто уже
согласился.

| 12 | Соглашение на получение рекламных материалов | Заполнен, но под другой сценарий — «Нажимая «Зарегистрироваться»...» (похоже, для формы регистрации на мероприятие) | Тот же незаполненный TEXT; использован в сегодняшнем тесте по умолчанию — не то, что нужно |
| 10 | Согласие на получение рекламных материало[в] | Полностью общий, ничего не заполнено | Общий шаблон-заготовка |

| 6 | Правила использования Битрикс24 Сайты | — | Служебный, не наш |
| 4 | Bitrix24 Sites Terms of Use | — | Служебный, не наш |
| **2** | Пример согласия на обработку персональных данных | — | ⚠️ Используется в проде CardScanner (`CONSENT_AGREEMENT_PD=2`) как реальный текст согласия на ПДн для посетителей выставок — но называется «ПРИМЕР», возможно не финализирован под АДАТ. Требует отдельной проверки/правки (не блокирует текущую задачу с email-рассылкой) |

**Перед реальным запуском — обязательно:** зайти в «Настроить» у id=14, заменить `[Кнопка]`
на реальное название кнопки (сама кнопка называется «Получать» — можно сослаться на неё же)
и `[Название организации]` на «ООО «АДАТ»» — правится только вручную через UI, программного
метода `userconsent.agreement.update` не существует (проверено — в REST есть только `.list`
и `.text` на чтение, `.consent.add` на запись).

## Побочная находка — CardScanner, отдельный параллельный канал согласий

`Bitrix24/CardScanner/` — PWA для менеджеров на выставках (фото визитки → OCR → контакт в Б24
+ экран согласия: QR-код или email → посетитель сам подтверждает). Реестр «Согласия
пользователей» на 24.09.2026 содержит 101 запись, большинство — не тестовые записи нашей
сессии, а история этого отдельного канала с 30.05.2026 (`Дело CRM #NNNN` — через CRM-формы,
`cardscan:token:...` — через сам сканер). Значительная часть ранних cardscan-записей
(`a-dat@a-dat.ru`, `az@bobp.ru`) — внутренние тесты команды, задокументированные в собственном
чек-листе проекта («Тест email-согласия — нужны сотрудники с реальными email», обновление
05.06.2026) — не реальные клиенты, подтверждено документально, не только на глаз.

Оба канала (CardScanner и Email-рассылки) пишут в один и тот же реестр `userconsent` —
конфликта нет, это два независимых легитимных способа получения согласия (очно на выставке
vs повторный запрос по email для уже существующей базы).
